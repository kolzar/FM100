# FM100 - Football Match Emotional System Architecture

## Project Overview

FM100 is a sophisticated football match simulation system that models emotional states of players and their impact on performance. The project demonstrates best practices for clean architecture, separation of concerns, and dependency injection in .NET 10.

## Architecture Layers

### 1. **FM100.Domain** - Pure Data Models
Contains only data classes with attributes (no calculation logic).

#### Domain Structure:
- **Base.Attribute/** - Core emotional and dynamic state models
  - `EmotionalState.cs` - Enum for player emotions
  - `MatchEmotionalState.cs` - Player emotional state during match (scale 1-20)
  - `MatchEvent.cs` - Event that occurred in match
  - `MatchEventType.cs` - Types of events (Goal, YellowCard, etc.)
  - `MentalAttributes.cs` - Player mental characteristics
  - `DynamicState.cs` - Team dynamic state
  - `SquadPerformanceSummary.cs` - Performance summary snapshot

- **FootballPlayer/** - Player models
  - `FootballPlayer.cs` - Player data model (extends Person)
  - `PlayerTechnicalAttributes.cs` - Technical skills (Passing, Shooting, etc.)
  - `PlayerSeasonStats.cs` - Season statistics

- **Base/** - Base classes
  - `Person.cs` - Base person attributes
  - `MentalAttributes.cs` - Mental attributes definition

**Key Principle**: Each domain class contains only properties with XML comments explaining their purpose.

### 2. **FM100.Core** - Business Logic Layer
Contains calculation services and core logic (no data storage).

#### Core Structure:
- **Performance/** - Performance calculation services
  - `MatchPerformanceCalculator.cs` - Player/squad performance calculations
  - `EmotionalStabilityCalculator.cs` - Emotional stability analysis
  - `DominantEmotionCalculator.cs` - Identifies dominant emotion
  - `SquadStrengthEvaluator.cs` - Squad strength evaluation

- **Performance/Abstractions/** - Service interfaces
  - `IMatchPerformanceCalculator.cs`
  - `IEmotionalStabilityCalculator.cs`
  - `IDominantEmotionCalculator.cs`
  - `ISquadStrengthEvaluator.cs`

- **DependencyInjection/** - DI setup
  - `PerformanceServiceCollectionExtensions.cs` - DI registration
  - `DI_SETUP_GUIDE.md` - DI documentation

- `MatchPerformanceExample.cs` - Example usage with DI

**Key Principle**: All calculation logic is encapsulated in services. Services are stateless (mostly singletons).

### 3. **FM100.UnitTest** - Test Suite
Comprehensive test coverage for each domain class and core service.

#### Test Structure (organized by component):
- **Domain/Attribute/** - Domain model tests
  - `MatchEmotionalStateTests.cs`
  - `DynamicStateTests.cs`
  - `MatchEventTests.cs`
  - `SquadPerformanceSummaryTests.cs`
  - etc.

- **Core/Performance/** - Service tests
  - `MatchPerformanceCalculatorTests.cs`
  - `EmotionalStabilityCalculatorTests.cs`
  - `DominantEmotionCalculatorTests.cs`
  - `SquadStrengthEvaluatorTests.cs`

## Key Design Patterns

### 1. **Separation of Concerns**
- **Domain** = Data only
- **Core** = Logic only
- **UnitTest** = Verification only

### 2. **Dependency Injection**
Services are registered and injected, not created directly:

```csharp
var services = new ServiceCollection();
services.AddPerformanceServices();
var serviceProvider = services.BuildServiceProvider();

// Services are available via DI
var calculator = serviceProvider.GetRequiredService<IMatchPerformanceCalculator>();
```

### 3. **Interface-Based Design**
All calculation services expose interfaces:
- `IMatchPerformanceCalculator`
- `IEmotionalStabilityCalculator`
- `IDominantEmotionCalculator`
- `ISquadStrengthEvaluator`

This enables:
- Easy mocking for unit tests
- Runtime implementation swapping
- Clear contracts between layers

### 4. **Single-File-Per-Type**
Each class, enum, and interface has its own file:
- Easier navigation
- Reduced merge conflicts
- Clear organization

### 5. **Documented Properties**
Every property includes XML comments explaining:
- Purpose
- Value range
- Impact on calculations

Example:
```csharp
/// <summary>
/// Player's happiness level (1-20).
/// Affects motivation and positive performance contributions.
/// </summary>
public int Happiness { get; set; } = 10;
```

## Emotional System

### Core Emotions (1-20 scale)
- **Happiness** - Positive mood, boosts motivation
- **Anger** - Can increase aggression or reduce focus
- **Fear** - Decreases confidence and risk-taking
- **Sadness** - Reduces motivation and engagement
- **Anxiety** - Decreases focus and accuracy

### Performance Factors
- **Stability** - Consistency of emotions (low variance = high stability)
- **Focus** - Concentration level
- **Determination** - Mental toughness
- **Motivation** - Drive to perform
- **Confidence** - Self-belief

### Event System
Match events trigger emotional responses:
- **Goal** - Increases happiness, motivation; decreases fear
- **GoalConceded** - Increases sadness, anxiety; decreases happiness
- **YellowCard** - Increases anxiety, anger
- **InjuryIncident** - Increases fear, anxiety; decreases motivation

## Calculation Formulas

### Player Performance Score
```
Performance = (Technical Average + Emotional Modifier) / 2
```

### Emotional Modifier
```
= Base(10) 
  + Happiness Bonus(0 to +5)
  + Anger Modifier(±3)
  - Fear Penalty(0 to -5)
  - Anxiety Penalty(0 to -5)
  - Sadness Penalty(0 to -3)
  + Focus Bonus(0 to +3)
  + Determination Bonus(0 to +2)
```

### Emotional Stability
```
High variance in emotions = Low stability
Low variance in emotions = High stability
Scale: 1-20
```

### Squad Strength
```
Overall Strength = (Technical + Emotional + Tactical) / 3
```

### Dependency Injection Setup
```csharp
public static IServiceCollection AddPerformanceServices(this IServiceCollection services)
{
	services.AddSingleton<IEmotionalStabilityCalculator, EmotionalStabilityCalculator>();
	services.AddSingleton<IDominantEmotionCalculator, DominantEmotionCalculator>();
	services.AddSingleton<IMatchPerformanceCalculator, MatchPerformanceCalculator>();
	services.AddScoped<ISquadStrengthEvaluator, SquadStrengthEvaluator>();
	return services;
```

## Best Practices Implemented

✅ **Single Responsibility** - Each class has one reason to change
✅ **Open/Closed** - Open for extension via interfaces, closed for modification
✅ **Dependency Inversion** - Depend on abstractions, not concretions
✅ **File Organization** - One type per file
✅ **Documentation** - XML comments on every property
✅ **Test Coverage** - Comprehensive unit tests
✅ **DI Pattern** - Services injected via constructor
✅ **Stateless Services** - Singletons for calculators
✅ **Clear Contracts** - Interfaces define service boundaries
✅ **Scalability** - Easy to add new emotions, events, or metrics
